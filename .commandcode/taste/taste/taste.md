# Taste

- Defers all UI/frontend work (dashboards, Next.js apps, visual consoles) until the underlying knowledge substrate is proven correct — explicitly states "Do NOT build a UI... yet" and "Design the minimal service boundary that the future UI will consume" rather than implementing it. Confidence: 0.9
- Prefers deterministic retrieval over ML/embeddings: will "first improve deterministic retrieval" (exact name matching, scoped package matching, phrase matching, evidence-aware ranking, deduplication, repository-aware filtering) and only introduces embeddings "if they are genuinely justified." Confidence: 0.9
- The system must remain fully testable and functional without `ANTHROPIC_API_KEY` set — falls back to a `MockProvider` (returns "I don't know" or a canned response) rather than throwing at construction time, so the entire pipeline (retrieval → citation → formatting) can be exercised offline. Confidence: 0.85
- Never makes a provider call during development if `ANTHROPIC_API_KEY` is unavailable; gates real LLM calls behind the env-var check. Confidence: 0.85
- Human/agent-authored `Decision` entities must remain explicitly distinguished from repository-derived facts — does not "invent decisions automatically." Decisions use `sourceType: human_statement` and `evidenceLevel: verified`; repository-derived facts use `sourceType: file` / `inferred_pattern`. The retrieval layer must be able to traverse `GOVERNS` and `VIOLATES` edges deterministically before any LLM is involved. Confidence: 0.9
- Does not claim the system is "production-ready" unless the implementation and tests actually support that conclusion — insists on a final validation pass (`pnpm -r typecheck`, `pnpm -r build`, `pnpm verify`) and explicit "I don't know" behavior when evidence is absent. Confidence: 0.85
- Optimizes for correctness of the underlying knowledge model over "visible progress" — explicitly: "Do not optimize for visible progress. Optimize for making Intel's underlying knowledge model correct." The pipeline is: repository reality → structured evidence → temporal graph → deterministic retrieval → trustworthy context → provider → cited intelligence → stable API → UI later. Confidence: 0.95
- Does not implement a giant AST/symbol-extraction system "unless the existing foundation is ready" — designs the parser→Symbol→EXPORTS/DEFINES/REFERENCES/DEPENDS_ON boundary first, documents supported languages and failure behavior, and starts with TypeScript/TSX only if contained and safe. Otherwise leaves a clean implementation boundary with tests/fixtures. Confidence: 0.85
- Acceptance suite questions each specify: expected retrieval evidence, expected relationship, expected provenance, and whether an LLM is required — the majority of the suite must NOT require an LLM. Uses fixtures and canonical FUSORB-ecosystem questions. Confidence: 0.85
- Documentation must be synchronized with the actual system and clearly separates status states: CURRENT, READY, DEFERRED, EXPERIMENTAL — never describes future functionality as implemented. Reads documentation files in full (not just the sections known to be wrong) to catch all drift, and describes status by what is built vs. not built rather than by session numbers (which go stale). Confidence: 0.85
- Final validation gate is the explicit trio: `pnpm -r typecheck` → `pnpm -r build` → `pnpm verify`, plus a deterministic `test` command (`vitest run`); documents exact PostgreSQL setup for database-backed tests. Confidence: 0.9
- Strict TypeScript configuration enforced: `noUncheckedIndexedAccess` makes array index access return `T | undefined` (requiring explicit null guards before property access, since `expect().toBeDefined()` does not narrow types), and `noUnusedLocals` disallows unused local variables. Confidence: 0.85
- Designs the minimal future API contract (operations for repository listing/detail, entity search, document reading, dependency inspection, graph traversal, decisions, violations, ingestion status, asking questions) as structured operations and documentation — defers full API implementation until the repository is ready. Confidence: 0.8
- Surfaces-collect-errors-rather-than-swallow — when auditing for the same class of gap that closed the citation-fabrication check, scans for results returned without full provenance and errors that get swallowed instead of surfaced; collects errors into a list/persisted field for diagnosis rather than silently ignoring or throwing. Confidence: 0.85
- Report-findings-then-fix-cheap — when auditing existing code for gaps, first reports all findings in full, then fixes what is cheap and safe to fix immediately, and explicitly lists what is not for a later pass rather than rushing incomplete or risky fixes. Confidence: 0.85
- Bounds-cost-of-data-processing — applies explicit file-count and file-size caps and skips node_modules/build-output when walking external repository trees; any unbounded input processing gets explicit limits to keep ingestion cost predictable. Confidence: 0.8
- Guarantees-idempotent-re-ingestion — re-running ingestion against the same commit must produce no duplicate rows; relies on upsert-by-natural-key and soft-delete-then-rebuild (removedAt on stale entities) so re-ingestion is safe and deterministic. Confidence: 0.85
- Explicit-per-session-scope — explicitly states what is in/out of each work session and resists scope creep, deferring adjacent features ("that's the next session") rather than extending scope beyond the current milestone. Confidence: 0.8
- Expects the assistant to handle the git commit as the final step of a completed work session after self-verifying all intended changes are in place — "if thats surely all.. i bet you can safely commit now" signals trust in the assistant to finalize and commit autonomously without further prompting. Confidence: 0.7
- Wants the architecture to be "internally consistent" as a distinct hardening goal — the database schema, Prisma client model, TypeScript types, runtime code, and documentation must all agree with each other. Performs reconciliation passes (not just implementation) to ensure all layers are aligned, surfacing mismatches as bugs to fix. Confidence: 0.85
- Explicitly wants systems to be "observable" as an architectural goal — core operations should expose internal metrics, diagnostics, and instrumentation (e.g., files parsed/skipped/errored, symbol counts, timing) so behavior is diagnosable, not just externally correct. Goes beyond error surfacing to include structured diagnostics persisted for later inspection. Confidence: 0.85
- Prefers a dedicated "hardening pass before freezing" workflow — after the initial build is far enough along, runs a disciplined audit-and-fix cycle (typecheck → build → test → verify) to stabilize the foundation, then freezes it before beginning the next phase (validation/expansion). Resists mixing new features into the hardening pass. Confidence: 0.8
- Insists on vendor-neutral provider abstraction — Intel is the knowledge substrate, not an Anthropic/OpenAI/Ollama application; models are interchangeable reasoning engines and the provider interface must remain independent of any specific vendor, with provider-specific concerns (model selection, API translation, credential handling) fully contained within each provider implementation. Confidence: 0.9
- No silent fallback to MockProvider for configured real providers — when a real provider is explicitly configured (e.g., INTEL_PROVIDER=anthropic) but its credentials or required configuration are missing, must produce a clear actionable error rather than silently falling back to MockProvider, since silent fallback can make a developer believe Intel is actually reasoning when it is not. Confidence: 0.9
- Inspects local environment before assuming machine state — before making decisions that depend on local system state (e.g., Ollama daemon reachability, installed models), verifies what is actually installed and running rather than assuming; reports clearly when expected tools or resources are absent. Confidence: 0.85
- Tests must not depend on live external APIs — unit tests must be fully offline and deterministic; integration tests for specific providers (e.g., Ollama) should be separate and only run when explicitly enabled (e.g., via env-var gate). Confidence: 0.85
- Avoids prematurely introducing complex abstractions — does not add streaming, tool calling, embeddings, agents, or complex provider-layer abstractions unless necessary for the current goal, but structures code so those capabilities can be added later without replacing the provider layer. Confidence: 0.85
- Preserves existing behavior when refactoring — when refactoring existing providers or shared code, must not regress citations, citation extraction, provenance validation, don't-know behavior, or warnings. Confidence: 0.85
- Respects existing environment conventions without overwriting — inspects existing environment files and configuration patterns before adding new ones; does not blindly overwrite existing .env files or committed configuration. Confidence: 0.8
- Shows provider/model info in CLI output without exposing secrets — makes it obvious which provider and model is being used (e.g., "Provider: ollama / Model: llama3.2:3b") without exposing API keys or credentials in output. Confidence: 0.8
- Prefers `pnpm exec` over `npx` for invoking project binaries — `npx` causes slow package resolution and hangs on Windows due to heavy `node_modules` I/O, while `pnpm exec` resolves immediately. Applies to vitest, tsup, and similar tools. Confidence: 0.9
- Uses provider-specific test config files (e.g., `--config vitest.provider.config.ts`) with `environment: "node"` and `envFile: false` rather than the root vitest config, which loads `.env` and triggers unwanted side-effects (e.g., PostgreSQL connections, env-dependent setup). Confidence: 0.85
- Verifies build success by checking for expected output files (`dist/index.js`, `dist/index.d.ts`) in addition to exit code — empty logs on success confirm tsup/typecheck only emit on errors. Confidence: 0.8
- When a background daemon (e.g., Ollama) is stuck consuming memory or not responding, force-kills it (`taskkill /f /im <name>.exe`) and restarts it rather than retrying against a degraded state. Confidence: 0.8
- Uses short-timeout `curl --max-time` probes for service health checks (e.g., `curl -s --max-time 5 http://localhost:11434/api/tags`) to detect daemon readiness without hanging indefinitely. Confidence: 0.75
- Responds to yes/no questions with a direct "Yes"/"No" followed by brief supporting specifics, rather than elaborating first. Confidence: 0.7
- Wants in-flight/uncommitted work committed and the tree left clean before any new work begins — "commit all changes before any new work" — rather than letting uncommitted changes pile up across sessions. Confidence: 0.7
- Works on a resource-constrained machine (8 GB RAM, ~320 GB HDD laptop) and wants to avoid heavy local runtimes — a past Docker installation crashed/overheated the machine and suffered constant updates, so prioritizes minimal-footprint local tooling and avoids installing memory/CPU-heavy tooling (e.g., Docker Desktop) on this laptop. Confidence: 0.75
- Values design that is explicitly "flexible, modular and futureproof" — favors general rules that apply to all consumers over targeted special-cases for the current instance, so the same behavior is correct for future/unseen repos without bespoke configuration. Confidence: 0.75
- Prefers being given an explicit, self-contained step-by-step guide to execute themselves over having the assistant provision things on their behalf — asks for "the step-by-step guide to fully do this on my own… so I do not drift and I can give the best report or feedback for any necessary fixes," and wants each step's exact commands plus what to capture (errors, logs) so their feedback is actionable. Confidence: 0.7
